# Sonic Pocket

A static recompilation of *Sonic the Hedgehog: Pocket Adventure* (Neo Geo
Pocket Color) to native C++.

The game's TLCS-900/H machine code is translated ahead of time into C++
functions, one per routine, and compiled into a native PC executable. The
translated code runs on a small Neo Geo Pocket Color runtime that provides the
video chip, sound chips, timers, interrupts, save flash and BIOS.

## Status

- **Playable.** `sonic-pocket` runs the recompiled game in an SDL3 window with
  keyboard and gamepad input, sound and persistent save data.
- **Exact.** `spa-verify` runs the recompiled game and an interpreter side by
  side and checks that registers, cycle counts, RAM and video memory stay
  identical every frame. Currently 1200 frames (boot, SEGA logo, title) are in
  exact lockstep.
- **Checked against a reference.** With the interpreter, the machine's work
  RAM matches a BizHawk (Mednafen) capture byte for byte for 1077 of 1198
  frames after boot; the remaining differences are understood timing details.
- **Nearly all native.** All 2,771 known routines are recompiled. Only the
  flash-save routine the game copies into RAM and the BIOS entry points run
  through the interpreter.

The generated code is correct but machine-shaped: every instruction calls the
CPU core's handler for it. Next steps are lifting it to plain, readable C++
and then rebuilding game systems (player, objects, collision) as structured
code, each change checked by the lockstep verifier. See
[`docs/recomp-plan.md`](docs/recomp-plan.md).

## How it works

```
cartridge ──► spa-recomp ──► generated C++ (one function per routine)
                                    │
                                    ▼
   runtime: TLCS-900/H CPU state + interpreter fallback, K2GE video,
            T6W28 PSG + DACs, Z80 sound CPU, timers/interrupts, flash,
            high-level BIOS  ──►  SDL3 frontend
```

- `src/cpu/tlcs900/`: MAME's TLCS-900/H core (BSD-3), adapted to run
  standalone. Its opcode tables drive both the interpreter and the recompiler.
- `src/ngpc/`: the machine: TMP95C061 timers and interrupts, K2GE video,
  T6W28 sound (from MAME), Z80 (superzazu/z80, MIT), flash and a high-level
  BIOS matching the Mednafen/BizHawk core.
- `src/recomp/`: `spa-recomp`, which decodes the ROM with the interpreter's
  tables and emits C++ with native control flow.
- `src/recomp_rt/`: runtime for the generated code: dispatch, calls and
  returns, interpreter fallback and the game thread.
- `src/apps/`: `sonic-pocket` (the game), `spa-verify` (lockstep check) and
  `ngpc-run` (headless interpreter runs and RAM dumps).
- `config/recomp/functions.txt`: routine entry points, generated by
  `tools/recomp_seeds.py` from ValleyBell's SPA disassembly.
- `docs/notes/`: reverse-engineering notes on the game's systems (scheduler,
  VBlank, input, player, collision, camera).
- `scripts/bizhawk-dump-reference.lua` and `tools/compare_ram_frames.py`:
  reference captures from BizHawk and comparison against the machine.
- `tools/rominfo.py`: checks that a cartridge image is the expected release
  ([`config/rom.json`](config/rom.json)).

## Building

Requirements: Visual Studio 2026 (or another C++20 compiler), CMake 4.2+ and a
legally obtained copy of the cartridge. SDL3 is downloaded automatically.

```powershell
cmake -S . -B build/recomp -G "Visual Studio 18 2026" -A x64 `
      -DSPA_ROM="C:/path/to/Sonic The Hedgehog - Pocket Adventure (World) (En,Ja).ngc"
cmake --build build/recomp --config Release --target sonic-pocket -- /m:1
```

The recompiler runs as part of the build and writes the generated sources to
`build/recomp/generated/`. They are large, so the first build takes a while;
on low-power machines keep to one compiler process as above.

## Playing

```powershell
build\recomp\Release\sonic-pocket.exe "path\to\cartridge.ngc"
```

| Action | Keyboard | Gamepad |
|---|---|---|
| Move | Arrow keys | D-pad / left stick |
| A | Z | South button |
| B | X | East button |
| Option | Enter | Start |
| Quit | Esc | |

The game runs at its own rate (about 59.95 frames a second, with the scenery
and sprites stepping every second frame) and each refresh of the monitor shows
a picture drawn between the game's frames, so motion follows the monitor's
refresh rate. Sound is kept in time by nudging the clock by a fraction of a
percent.

`--aspect original|16:10|16:9` picks the shape of the picture (`--widescreen`
is 16:9); Tab or F10 cycles through them while playing and the last choice is
remembered. In a level a wide view shows the level itself beyond the original
screen's edges, read from the cartridge, with the HUD at the edges; every other
screen (title, menus, special stages) is the original 160x152 centred with
black bars. The game is told to keep the sprites and objects of the extra
width (it normally drops anything off the 160-pixel screen), so a platform or
an enemy is there as the wide picture reaches it. The zone's title card is
centred over the level, which is already where it will be. Where the camera is
locked at the end of an act 1 and in the boss arenas (every zone's boss but the
third's, which has no lock, and the last fight), the level is shown beyond the
screen instead of black bars and the player may walk to the edges of the picture,
on a floor the wide view fills in where the level's data stops short (the last 64
pixels of the level, never seen before; where an arena's last wall ends before the
data does, the wall's last column of tiles is repeated); the first zone's boss goes
the whole width. The third zone's boss is as it was. The fifth zone's flight shows its
plane once (it is a picture the game slides, which wrapped round into the extra width),
and its two flapping bird robots start beyond the picture and fly in. Those are
the things a wide view does to the game itself: objects wake up a little
earlier, the player and the first boss get more room, and the longer sprite
list can move the game's tick by a frame, so a recording made in one aspect plays
back exactly only in that aspect. A wide view also eases the vertical camera, which
the game starts and stops abruptly (the horizontal one follows Sonic's speed): the
level and the sprites move together, up to 12 pixels from where the game has them,
and the game keeps the sprites of that margin above and below the screen as it does
those at the sides.

The picture is fitted to the window by `--scale-mode`: `sharp` (the default; F8 cycles
the modes and the choice is remembered) fills the window with evenly wide pixels at any
size, `integer` uses whole multiples with bars (270 x 7 = 1890 pixels at 1080p), and
`nearest` is plain scaling, which gives pixels of two different widths unless the window
happens to be a whole multiple. F11 or Alt+Enter toggles borderless fullscreen. The window
is made with a high pixel density, so a Retina display is drawn in its own pixels and not
scaled up (and softened) by the system. The sound is kept `--audio-latency` frames deep
(default 2, about 36 ms; it raises itself by a frame if the device runs dry), where it was
4 (about 67 ms). `--frame-delay` (`auto`, `off` or milliseconds) waits before reading the
buttons so that they are read late in the refresh; `auto` does this only where a refresh is
12 ms or longer (60 Hz) and is off on a faster display, where there is little to gain.
`--stats` reports how long a key press takes to reach a presented picture and how deep the
sound queue was. `--window WIDTHxHEIGHT` sets the window's size, and `--screenshot file.png
[--screenshot-at FRAME]` writes the window's picture (in the display's pixels) and quits.

Options: `--scale N` (window size, default 4), `--japanese`,
`--no-smoothing` (show only the game's own frames),
`--fps N` (present N pictures a second by the clock instead of waiting for the
monitor), `--stats` (print how evenly pictures were presented, and how evenly the
game's clock stepped, when the window closes; `--quit-after SECONDS` closes it for you), and
`--interpreter` to run the same game on the interpreter instead of the
recompiled code. `--record input.txt` logs every frame's buttons from a fresh
cartridge (the save file is untouched), `--replay input.txt` plays such a log
back in the window, and F9 bookmarks the frame on screen;
`ngpc-run --rom <cartridge> --input input.txt --bookmarks input.txt.bookmarks`
then replays the session headlessly and writes a contact sheet of the real and
in-between pictures around each bookmark. Save data is stored in the SDL preferences folder
(`%APPDATA%\SonicPocket\SonicPocket\flash_save.bin` on Windows).

## Verifying

```powershell
cmake --build build/recomp --config Release --target spa-verify -- /m:1
build\recomp\Release\spa-verify.exe --rom "path\to\cartridge.ngc" --frames 1200
```

To compare the machine against BizHawk, capture a reference with
`scripts/bizhawk-dump-reference.lua` (see its header), dump the same frames with
`ngpc-run --dump-ram`, and run `tools/compare_ram_frames.py`.

## Repository policy

This repository contains no ROM data, extracted assets, BIOS or generated
code. The recompiled C++ is produced at build time from your own cartridge.
Committed files are original code, MIT/BSD-licensed third-party code with its
notices, and facts about the ROM such as routine addresses.
